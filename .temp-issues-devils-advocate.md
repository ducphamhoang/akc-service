## Critical Failure Modes

### CF1 — The `save_all_patterns` Read-Modify-Write Race = Full KB Corruption
**Severity:** CRITICAL - Silent Data Loss
**Files:** `akc_service/learning_integration.py` (line 539-635, 163-168)

**Failure Scenario:**
```
Worker A: load_all_patterns() [reads 200 patterns with P1:0.50]
Worker B: append_pattern_version(P2) [acquires LOCK_EX, appends P2 to file]
Worker A: update P1.confidence = 0.55
Worker A: save_all_patterns() [overwrites file with 200 patterns, P2 IS GONE]
```

**Why It's Bad:**
- No exception is raised
- No warning is logged
- Pattern P2 is silently lost forever
- Invisible data corruption

**Under Load:**
- Every `/record` triggers `apply_confidence_delta` in background
- Multiple background tasks can run concurrently
- Under real load (10+ requests/sec) this race will trigger regularly

**Impact:** KB data loss without any signal

### CF2 — Fire-and-Forget `/record` Has No Delivery Guarantee
**Severity:** CRITICAL - Permanent Data Loss
**Files:** `akc_service/routes.py` (line 355), `learning_integration.py` (line 469)

**Failure Scenario:**
```
1. POST /record → returns 202 Accepted immediately
2. Queues apply_confidence_delta() as FastAPI BackgroundTask
3. Response sent to client
4. Process crashes / OOM killer / systemd restart (before task runs)
5. Confidence delta is PERMANENTLY LOST with no error
```

**Why It's Bad:**
- No dead-letter queue
- No retry mechanism
- No acknowledgement that update ever happened
- 202 response is a lie (says "accepted" but means "queued in-memory")

**Real Scenario:**
- Service runs under memory pressure
- Dozens of task outcomes recorded (202 returned)
- Process gets OOM killed or restarted
- Zero confidence updates applied
- KB reflects maybe 60% of actual outcomes
- Confidence values drift systematically

**Impact:** KB learns from incomplete/biased task stream, confidence becomes unreliable

### CF3 — `/update` Endpoint Is Unauthenticated Confidence Bomb
**Severity:** CRITICAL - Safety Bypass
**Files:** `akc_service/routes.py` (line 549-676), `main.py` (line 83-89)

**Failure Scenario:**
```bash
curl -X POST http://localhost:8000/akc/v1/update \
  -H "Content-Type: application/json" \
  -d '{"pattern_id": "pat-001", "new_score": 0.95, "reason": "legit"}'
```

**Result:** Pattern confidence is now 0.95 (Gold tier) with no authorization

**Why It's Bad:**
- Zero authentication
- CORS only blocks browsers, not curl/scripts/server-to-server
- Bypasses guardrail G6 (requires override key) because endpoint skips `check_guardrails()`
- Any pattern can be force-promoted to Gold tier

**Real Scenario:**
- Misconfigured script accidently calls this endpoint with wrong patterns
- Internal tool running on same host sends wrong data
- Pattern confidence becomes corrupted
- System trusts corrupted confidence values

**Impact:** Confidence values become user-controlled (on local network), guardrails meaningless

## Medium Risks

**Severity:** MEDIUM - Broken Incident Response
**Files:** `akc_service/validation_engine.py` (line 1072-1131)

**Failure Scenario:**
```
rollback("fix-001")
# → logs to confidence_history.jsonl: "new_confidence: 0.0"

# → DOES NOT update patterns.jsonl
```

**Why It's Bad:**

- Nothing actually happens
- Pattern continues affecting game
- Operator thinks rollback succeeded

**Impact:** Broken incident response - can't revert bad fixes

### MR2 — `load_all_patterns()` With No Cache = Latency Degradation
**Severity:** MEDIUM - SLA Breach Inevitable
**Files:** `routes.py` (called by every `/query`, `/fix`, `/stats`)

**Failure Scenario:**
```
# Day 1: 50 patterns, load_all_patterns = 5ms
# Month 3: 5,000 patterns (append-only with versions), load_all_patterns = 200ms
# Month 6: 15,000 patterns, load_all_patterns = 500ms ← SLA BREACHED (50ms budget)
```

**Why It's Bad:**
- Every request reads full file
- No pagination, no cache, no index
- File grows unboundedly (append-only, no compaction)
- Latency scales O(n) with KB size

**Real Scenario:**
- System runs for 6 months
- Gradual latency increase (not visible at first)
- After 6 months: 70% of requests timeout
- No sharp failure point - gradual degradation

**Impact:** SLA violation inevitable after a few months of operation

## Cascading Failure Scenarios

### Scenario A: KB File Grows Unbounded, SLA Breaches
1. Each `/record` triggers `apply_confidence_delta` → `save_all_patterns` (full rewrite)
2. `append_pattern_version` also appends for other updates
3. File grows without deduplication
4. After 3 months: `load_all_patterns()` takes 400ms
5. `/query` violates 50ms SLA consistently
6. Service is "healthy" (200s everywhere) but degraded

### Scenario B: Bad Fix Deployed, Rollback Fails
1. Fix deployed, causes error rate spike
2. Operator calls `rollback("fix-001")`
3. Audit trail updated, KB unchanged
4. Game continues to see bad pattern
5. Error rate persists
6. Operator confused why rollback had no effect

### Scenario C: Process Crashes Lose Confidence Updates
1. 10 task outcomes recorded → 10 × 202 Accepted
2. Process OOM killed before background tasks run
3. Zero KB updates applied
4. Service restarts, starts learning from (stale confidence) + (new outcomes only)
5. Over time, confidence values drift to not match actual success rates

## Questions That Must Be Answered

1. **Is there anywhere in production where akc-service handles concurrent requests?** If yes, CF1 is actively producing data corruption.

2. **What is the actual accumulated size of patterns.jsonl today?** If >1000 lines, latency is already drifting.

3. **Has the rollback path ever been end-to-end tested?** Given that rollback doesn't modify patterns.jsonl, how was this caught?

4. **What happens to sync pending queue if remote is down 48 hours?** Queue grows unboundedly in `sync_state.json`, no size limit, no expiry.

5. **Is there a defined recovery procedure for KB corruption?** If patterns.jsonl is malformed mid-file, what's the recovery?

---

## Summary

**The system will work correctly for happy-path testing in a single-process, low-load, cooperative environment. It will fail silently and accumulate correctness debt under production conditions: restarts, concurrent writes, operator intervention, or adversarial input.**

**Most dangerous property:** Most failure modes produce no exception and no log entry — they simply do nothing while the system appears healthy.
